# Лабораторная №5 простыми словами

## Что изменилось по сравнению с предыдущими работами

Представь гостиницу. До этой работы у нас был работающий сервер, но он не имел
настоящего постоянного хранилища. После этой работы появилась база PostgreSQL,
в которой можно хранить гостей, отели, номера, бронирования и отзывы.

Самая короткая формулировка для защиты:
«Я подключил сервер бронирования отелей к PostgreSQL. Структуру базы описал SQL-миграцией,
а базу, мигратор и приложение запускаю вместе через Docker Compose. Проверил откат,
сохранение данных и ответ 503 при недоступности базы».

## PostgreSQL, таблица, строка, ключ

PostgreSQL — программа, управляющая базой данных. База hotels — наше хранилище.
Таблица похожа на аккуратную таблицу Excel, но СУБД дополнительно проверяет связи,
типы данных и ограничения. Одна строка rooms — один номер определённого отеля.

Пять таблиц находятся в migrations/000001_init_schema.up.sql:

| Таблица | Что хранит | Пример |
|---|---|---|
| users | Пользователей | Гость с email и именем |
| hotels | Отели | Отель «Центральный» в Казани |
| rooms | Номера | Номер 101, STANDARD, 3000.50 за ночь |
| bookings | Бронирования | Гость бронирует номер с 10 по 12 ноября |
| reviews | Отзывы | Оценка 5 и комментарий |

id — уникальный идентификатор UUID. Первичный ключ (PK) однозначно определяет строку.
Внешний ключ (FK), например rooms.hotel_id, связывает номер с существующим отелем.
База не разрешит создать номер для несуществующего отеля.

NOT NULL запрещает отсутствие обязательного значения. UNIQUE запрещает повтор:
email уникален у пользователя, а пара hotel_id + room_number уникальна у номера.
CHECK проверяет правило: цена неотрицательна, вместимость больше нуля,
дата выезда позже даты заезда.

ON DELETE определяет поведение при удалении родительской строки.
RESTRICT запрещает удаление, пока есть зависимые записи: номер с бронями нельзя
удалить незаметно вместе с историей. CASCADE удаляет зависимые отзывы вместе с их
автором/отелем. Само каскадное правило не обходит другие ограничения RESTRICT.

Индекс — дополнительная структура для быстрого поиска. Аналогия: алфавитный
указатель книги. Для бронирований по room_id база быстрее находит нужные строки.
Индекс занимает место и замедляет запись, поэтому не стоит создавать лишние.

## Зачем нужна миграция

Миграция — пронумерованное изменение структуры БД, сохранённое рядом с кодом.
В up.sql находятся CREATE TABLE и CREATE INDEX.
В down.sql — обратные DROP TABLE. Сначала удаляем reviews и bookings, затем rooms,
hotels и users: иначе внешние ключи запретят удалить таблицу, на которую ещё ссылаются.

migrate запускает SQL и запоминает version=1, dirty=false в schema_migrations.
Повторный up не создаёт таблицы заново: он сообщает no change.
dirty=true означает, что миграция не была успешно завершена; нельзя просто
игнорировать это состояние или без разбора объявлять версию успешной.

Миграция — не резервная копия. После DROP TABLE повторный up восстановит структуру,
но не удалённые строки. Поэтому проверка отката выполняется в отдельной временной БД.

## Что делает Docker Compose

Dockerfile описывает один образ приложения. docker-compose.yml описывает совместную
работу нескольких контейнеров. У нас их три:

1. db запускает PostgreSQL.
2. migrate ждёт готовности db, применяет миграции и завершается с кодом 0.
3. app ждёт готовности db и успешного migrate, затем запускает Python-сервер.

healthcheck базы выполняет pg_isready. Просто «контейнер запущен» ещё не означает,
что PostgreSQL закончил инициализацию. Поэтому нужны service_healthy и
service_completed_successfully.

Внутри контейнера localhost означает этот же контейнер. Приложение обращается к
db:5432 — Docker сам находит контейнер с именем сервиса db.
С компьютера обращаемся к 127.0.0.1:5435: это опубликованный порт PostgreSQL.
А HTTP открыт на 127.0.0.1:8085, который перенаправлен на app:8080.

pgdata — именованный том: отдельное хранилище данных PostgreSQL. Контейнер можно
пересоздать, а том подключить снова. docker compose down сохраняет том,
docker compose down -v удаляет и том.

## Конфигурация, пароль и пул соединений

.env хранит настройки конкретного компьютера. .env.example — безопасный шаблон
без настоящего пароля. settings.py читает DB_HOST, DB_PORT, DB_USER, DB_PASSWORD,
DB_NAME и DB_MAX_CONNS. При отсутствии обязательного значения приложение завершается
с понятным сообщением. DB_PORT и DB_MAX_CONNS имеют проверяемые значения по умолчанию.

Соединение — установленный канал общения приложения с базой. Открывать новый канал
на каждый запрос дорого. Пул — небольшой запас готовых соединений:
взять, выполнить SQL, вернуть. Он реализован в internal/database/postgres.py.
Верхняя граница — 10 соединений по умолчанию; одновременно бесконечно много
соединений не откроется. Если все заняты, запрос немного ждёт, затем получает ошибку.

При старте connect делает до 10 попыток подключения. Это полезно при задержке запуска
или перезапуске базы. Пауза между попытками ограничена 5 секундами.
Сами SQL-запросы и ожидание соединения тоже ограничены по времени.

## Как работает /health

Путь запроса:
браузер/curl -> HealthHandler -> HealthService -> PostgresHealthRepository -> пул -> PostgreSQL.

Репозиторий выполняет SELECT 1. Это очень простой запрос, который подтверждает,
что приложение действительно может общаться с БД. Сервис формирует результат,
а HTTP-обработчик выбирает код ответа:

- 200 и db=up — база отвечает;
- 503 и db=down — приложение работает, но его зависимость недоступна.

После docker compose start db пул восстанавливает соединения, и /health снова
возвращает 200. При этом проверка доступности не проверяет все таблицы и все
бизнес-сценарии: её смысл — проверить соединение с базой.

## Что показать преподавателю

Открой docker-compose.yml и миграции. Запусти docker compose ps -a.
Покажи /health, список таблиц и schema_migrations.
Затем запусти python scripts/verify_lab5.py: он воспроизводит все основные проверки.
Реальные результаты сохранены в docs/evidence/lab5.json и в отчёте.

## Краткие ответы на контрольные вопросы

1. **Зачем down и почему откат опасен?** Down отменяет изменение схемы. DROP удаляет
   данные, поэтому повторный up их не возвращает; в production часто нужна новая
   исправляющая миграция.
2. **Почему нельзя менять применённую миграцию?** Разные базы получат разную схему
   с одним номером. Инструмент хранит применённую версию в schema_migrations;
   новые изменения оформляются новым файлом.
3. **Почему недостаточно depends_on?** Запуск контейнера не равен готовности базы.
   Healthcheck проверяет готовность. Повторные подключения нужны и при последующих сбоях.
4. **Зачем pgdata?** Том сохраняет данные независимо от контейнера. down сохраняет,
   down -v удаляет том и данные.
5. **localhost или db?** В Compose приложение использует db:5432. При запуске Python
   на компьютере — 127.0.0.1 и опубликованный порт 5435.
6. **Что такое пул и зачем ограничение?** Набор повторно используемых соединений.
   Сумма размеров пулов всех экземпляров должна быть меньше max_connections PostgreSQL
   с запасом для мигратора и администратора.
7. **Почему пароль не в коде?** Код и Git-история доступны другим людям. Настоящий
   пароль находится в исключённом .env; .env.example содержит только шаблон.
8. **Индексы FK и ON DELETE?** PostgreSQL не создаёт индекс дочернего FK автоматически.
   Индекс ускоряет поиск связей. CASCADE удаляет зависимые записи, RESTRICT запрещает
   удаление родителя, SET NULL оставляет дочернюю запись без связи, если поле допускает NULL.
