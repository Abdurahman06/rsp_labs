# Отчёт по лабораторной работе №7

**Тема:** Service Layer и CRUD-операции REST API.  
**Предметная область:** бронирование номеров в городских отелях.  
**Основа:** репозитории и схема PostgreSQL из ЛР5–6.

## Цель

Разделить транспортный слой, бизнес-логику и доступ к данным; связать HTTP-маршруты с сервисами; возвращать подходящие HTTP-коды; проверять бизнес-логику без сервера и настоящей БД.

## Схема запроса

```text
HTTP/JSON -> ApiHandler -> DTO -> HotelService / BookingService
                                     |                 |
                                     v                 v
                               HotelRepository      UnitOfWork
                                     |                 |
                                     +---- PostgreSQL -+
```

- **Контроллер** разбирает HTTP и JSON, вызывает сервис, формирует JSON и статус. SQL и бизнес-правил в нём нет.
- **DTO** (`internal/controller/dto.py`) задают форму запроса и ответа. Ответы переводятся в camelCase (например, `check_in_date` → `checkInDate`). `password_hash` не сериализуется.
- **Сервис** (`internal/service/`) выполняет правила предметной области, не зная об HTTP.
- **Репозиторий** выполняет параметризованные SQL-запросы к PostgreSQL.
- **Unit of Work** группирует связанные операции бронирования в транзакцию.

Зависимости передаются через конструкторы/корень сборки в `cmd/app/main.py`: сервис получает репозиторий или Unit of Work извне. Тесты вместо PostgreSQL передают fake-объекты.

## Бизнес-правила и ответы

| Правило | Ошибка предметной области | HTTP |
|---|---|---|
| Дата выезда должна быть позже даты заезда | `ErrInvalidInput` | 400 |
| Нельзя бронировать на прошедшую дату | `ErrInvalidInput` | 400 |
| Пользователь и номер должны существовать | `ErrNotFound` | 404 |
| Номер должен быть доступен | `ErrConflict` | 409 |
| Даты брони не пересекаются с действующей бронью | `ErrConflict` | 409 |
| Нельзя отменить бронь повторно | `ErrConflict` | 409 |
| Отель нельзя удалить, пока на него ссылаются номера | `ErrConflict` из PostgreSQL | 409 |
| Неожиданная ошибка хранилища | `RepositoryError` | 500 |

При создании ресурса сервер отвечает `201 Created` и передаёт путь ресурса в `Location`. Успешное чтение/изменение — `200 OK`; удаление — `204 No Content` без тела.

## Реализованные маршруты

| Метод | Путь | Действие |
|---|---|---|
| POST | `/api/v1/hotels` | Создать отель |
| GET | `/api/v1/hotels?limit=20&offset=0` | Получить страницу списка |
| GET | `/api/v1/hotels/{hotelId}` | Получить отель |
| PUT | `/api/v1/hotels/{hotelId}` | Полностью изменить отель |
| DELETE | `/api/v1/hotels/{hotelId}` | Удалить отель |
| POST | `/api/v1/bookings` | Создать бронь |
| GET | `/api/v1/bookings/{bookingId}` | Получить бронь |
| POST | `/api/v1/bookings/{bookingId}/cancel` | Отменить бронь |

JSON-запрос бронирования:

```json
{
  "userId": "UUID существующего пользователя",
  "roomId": "UUID существующего номера",
  "checkInDate": "2027-01-10",
  "checkOutDate": "2027-01-12"
}
```

Для учебного запуска `userId` приходит в теле запроса. Это упрощённая подстановка пользователя, потому что полноценная JWT-аутентификация из контракта ЛР2 не была реализована предыдущими этапами.

## Изменения в коде

- `internal/service/hotel_service.py`: валидация, создание, получение, постраничный список, полное изменение и удаление отеля.
- `internal/service/booking_service.py`: проверка периода, даты, пользователя, доступности номера и пересечения броней; расчёт суммы; отмена.
- `internal/controller/api_handler.py`: REST-маршруты и единая функция `error_response` для преобразования ошибок предметной области в HTTP-коды.
- `internal/controller/dto.py`: отдельные классы DTO для входных запросов и явное преобразование доменных объектов в публичные ответы.
- `internal/repository/interfaces.py` и `internal/repository/postgres/`: добавлены обновление отеля и смена состояния брони.
- `openapi.yaml`: описаны CRUD отелей и создание/отмена брони.
- `tests/test_services.py`: три модульных сценария с fake-репозиториями без PostgreSQL.

## Проверка и демонстрация

```powershell
Copy-Item .env.example .env   # выполнить только если файла .env нет
docker compose up --build -d
python -m unittest tests.test_services -v
curl.exe -i http://127.0.0.1:8086/health
```

Создание отеля:

```powershell
curl.exe -i -X POST http://127.0.0.1:8086/api/v1/hotels `
  -H "Content-Type: application/json" `
  -d '{"name":"Отель Демонстрация","city":"Симферополь","address":"ул. Примерная, 1","rating":4.5,"description":"Учебная запись"}'
```

В `Location` появится `/api/v1/hotels/{id}`. Подставив этот ID, показать GET, затем полное изменение:

```powershell
curl.exe -i http://127.0.0.1:8086/api/v1/hotels/{id}
curl.exe -i -X PUT http://127.0.0.1:8086/api/v1/hotels/{id} `
  -H "Content-Type: application/json" `
  -d '{"name":"Отель Демонстрация","city":"Симферополь","address":"ул. Примерная, 2","rating":4.7,"description":"Обновлено"}'
curl.exe -i -X DELETE http://127.0.0.1:8086/api/v1/hotels/{id}
```

Для бронирования нужны UUID существующего пользователя и номера из базы. Успешное бронирование демонстрирует расчёт `totalCost`; повторное бронирование пересекающихся дат возвращает 409. Попытка создать бронь с прошедшей датой возвращает 400. Список тестов проверяет запрет прошедшей даты, успешный расчёт и недоступное состояние номера.

## Вывод

Сервисный слой отделяет правила от HTTP и SQL. Отели доступны через полный CRUD REST API, а бронирования проходят проверку связанных сущностей, статуса номера и пересечения дат в транзакции. Общий обработчик переводит доменные ошибки в стабильные HTTP-коды. Модульные тесты запускаются отдельно от инфраструктуры.
