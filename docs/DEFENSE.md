# Лабораторная №6 простыми словами

## Главная идея

В пятой работе мы организовали место хранения данных — PostgreSQL.
В шестой научили программу аккуратно с ним работать: создавать, находить,
изменять и удалять данные через отдельный слой Repository.

Для защиты можно начать так:
«Я реализовал слой доступа к данным для системы бронирования отелей.
Сервисы работают через интерфейсы репозиториев, а конкретные SQL-запросы находятся
в PostgreSQL-реализациях. Проверил CRUD, обработку ошибок, защиту от SQL-инъекций
и транзакционное бронирование на настоящей базе».

## Что такое слои и зачем они нужны

Представь обращение гостя на стойку отеля.

- **HTTP-обработчик** — сотрудник, принимающий обращение. Разбирает адрес и параметры,
  возвращает JSON и HTTP-код. Код: internal/controller/lab6_handler.py.
- **Сервис** — сотрудник, знающий правила. Например, нельзя забронировать занятый
  на эти даты номер. Код: internal/service/booking_service.py.
- **Репозиторий** — сотрудник, работающий с картотекой. Умеет найти номер или сохранить
  бронь. Код: internal/repository/postgres/.
- **PostgreSQL** — сама картотека с правилами целостности.

Сервис решает, *можно ли* сделать бронь. Репозиторий выполняет, *как сохранить*
её в базе. Поэтому в BookingService нет SQL, а репозиторий не устанавливает
HTTP-коды ответа.

## Модель, интерфейс и реализация — разные вещи

**Модель** описывает данные. Например, Room содержит hotel_id, room_number,
price_per_night, capacity и другие поля таблицы rooms.
Модели находятся в internal/domain/models.py. Это Python dataclass —
класс, для которого Python автоматически создаёт конструктор и сравнение.

**Интерфейс** описывает доступные действия без SQL.
В internal/repository/interfaces.py у RoomRepository написано:
create, get_by_id, list, delete, update, get_for_update.
Protocol означает: «любой объект с такими методами подходит под этот контракт».
Он помогает типизации и архитектуре; сам Protocol не выполняет запросы.

**Реализация** знает конкретный способ хранения.
PostgresRoomRepository в internal/repository/postgres/room.py выполняет SQL.
Вместо него для модульного теста сервиса можно передать объект, хранящий комнаты
в обычном словаре. Сам сервис менять не нужно — это инверсия зависимостей.

main.py собирает объекты: создаёт пул, четыре репозитория, CatalogService,
BookingService и HTTP-сервер. Передача готового репозитория в конструктор сервиса
называется внедрением зависимостей (Dependency Injection).

## Что означает CRUD и где он сделан

CRUD — четыре основные операции над данными.

| Буква | Операция | Метод Python | SQL | Пример для отеля |
|---|---|---|---|---|
| C | Create — создать | create | INSERT | Добавить номер 101 |
| R | Read — прочитать | get_by_id, list | SELECT | Найти номер или список |
| U | Update — изменить | update | UPDATE | Изменить цену номера |
| D | Delete — удалить | delete | DELETE | Удалить номер без броней |

Для users, hotels, rooms и bookings реализованы create, get_by_id, list, delete.
Для rooms дополнительно сделан update, для users — get_by_email.
Методичка требует минимум три сущности — у нас четыре. Review описан как модель,
но отдельный репозиторий отзывов в этой работе не требуется.

Общая механика находится в base.py: взять соединение, выполнить параметризованный
запрос, преобразовать результат, вернуть соединение. Каждый конкретный репозиторий
содержит свои фиксированные SQL-запросы и явный список столбцов.

## Что происходит при создании номера

1. Программа создаёт Room с hotel_id, номером, ценой и вместимостью.
2. Вызывает rooms.create(room).
3. Репозиторий берёт соединение из пула.
4. Выполняет INSERT с параметрами.
5. PostgreSQL проверяет FK, UNIQUE, CHECK и NOT NULL.
6. База генерирует UUID и created_at.
7. RETURNING возвращает эти поля вместе с остальными данными.
8. Репозиторий возвращает новую заполненную модель Room, а соединение — в пул.

Важно: в нашей Python-реализации create **возвращает новый объект**, а не меняет
переданный. Поэтому пишем saved = repo.create(room). У saved уже есть id и created_at.

Если попытаться добавить второй номер 101 в тот же отель, UNIQUE запретит вставку.
В другом отеле номер 101 допустим: уникальна пара hotel_id + room_number.

## Что такое SQL-инъекция

SQL — язык команд для базы. Инъекция возникает, если пользовательский текст
склеивается с SQL и становится частью команды.

Правильный запрос в user.py выглядит так:

```python
cur.execute("SELECT id, email FROM users WHERE email = %s", (email,))
```

%s здесь — место для параметра драйвера, а не подстановка через оператор % Python.
Текст запроса и значение передаются отдельно. Поэтому строка
`' OR '1'='1` воспринимается как искомый email, а не как условие «вернуть всех».

В тесте сначала есть реальный пользователь, затем выполняется поиск по вредоносной
строке. Получаем ErrNotFound. Дополнительно проверяется, что таблица и пользователь
сохранились.

Параметризуются значения. Имя таблицы, столбца и ASC/DESC нельзя передать как обычное
значение. Если нужна динамическая сортировка, допустимые поля проверяют по белому
списку. У нас порядок фиксированный — пользователь его не меняет.

## Как устроены ошибки

База говорит техническими кодами. Остальная программа должна понимать их смысл
без знания драйвера psycopg.

| Что случилось | Ошибка программы | Пример в гостинице | HTTP |
|---|---|---|---|
| Строка не найдена | ErrNotFound | Номера с таким id нет | 404 |
| Нарушена уникальность | ErrAlreadyExists | Email уже зарегистрирован | 409 |
| Нарушена связь/занят ресурс | ErrConflict | Номер с бронями нельзя удалить | 409 |
| Неверное значение | ErrInvalidInput | Отрицательная цена или неверный UUID | 400 |
| Другой сбой БД | RepositoryError | Сетевой сбой или таймаут | 500 |

Преобразование SQLSTATE находится в postgres/db.py:
23505 -> ErrAlreadyExists; 23503 -> ErrConflict; 23514, 23502, 22P02 и некоторые
ошибки формата -> ErrInvalidInput. Если SELECT ничего не нашёл, fetchone()
возвращает None — base.py создаёт ErrNotFound.

Для UPDATE и DELETE проверяется rowcount. Если затронуто ноль строк,
записи не было: нельзя сообщать об успешном изменении несуществующего номера.

Исходная ошибка сохраняется через `raise ... from exc` и доступна в __cause__
для диагностики. Клиент не получает SQL, пароль или технические детали драйвера.
HTTP-код выбирает только обработчик в controller.

## Пагинация: зачем limit, offset и ORDER BY

Пагинация — выдача большого списка частями.
list(limit=20, offset=40) означает: пропустить 40 записей, вернуть следующие 20.

В SQL используется ORDER BY created_at DESC, id:
сначала новые записи, а при одинаковом времени — однозначный порядок по UUID.
Без ORDER BY база не обязана возвращать строки в одном порядке.

У limit верхняя граница 100. Отрицательный offset и неположительный limit
возвращают ErrInvalidInput. Пустая страница — обычный пустой список, это не ошибка.
При одновременном добавлении данных OFFSET-пагинация всё равно может сдвигаться;
для больших меняющихся списков используют keyset-пагинацию по последнему ключу.

## Почему цена — Decimal

Обычный float хранит приближённые двоичные дроби. Для денег это приводит к
нежелательным округлениям. PostgreSQL хранит цену как NUMERIC(12,2), Python —
как Decimal. Пример: 3000.50 × 2 ночи = ровно 6001.00.
В демонстрационном JSON деньги передаются строкой, чтобы сохранить точность.

password_hash — конфиденциальное поле. Оно исключено из repr и из JSON через
to_public. Само repr=False не защищает JSON: нужен отдельный сериализатор.
В коде используется именно to_public; произвольный dataclasses.asdict(User)
использовать для публичного ответа нельзя. Авторизация и хеширование настоящих
паролей находятся за пределами ЛР6; строки hash в тестах — фиктивные данные.

## Транзакция и защита от двойного бронирования

Дополнительное задание реализовано в BookingService.book.

Допустим, гость бронирует номер 101 с 10 по 12 марта:

1. Сервис открывает транзакцию через Unit of Work.
2. rooms.get_for_update выполняет SELECT ... FOR UPDATE и блокирует строку номера.
3. Проверяется существование гостя и доступность номера.
4. bookings.has_overlap ищет действующую бронь на пересекающиеся даты.
5. Если всё свободно, вычисляется сумма и создаётся бронь.
6. COMMIT сохраняет изменения и освобождает блокировку.
7. При любой ошибке выполняется ROLLBACK — незавершённые изменения отменяются.

Unit of Work — объект, объединяющий несколько репозиториев одной транзакцией.
Все они получают одну и ту же connection. Иначе каждый репозиторий мог бы взять
своё соединение, и общей атомарной операции не получилось бы.

Пересечение проверяется так:

```text
существующий_заезд < новый_выезд
И существующий_выезд > новый_заезд
```

Промежуток рассматривается как [заезд, выезд): день выезда не занят этой бронью.
Поэтому 10–12 марта и 12–13 марта совместимы, а 10–12 и 11–13 — пересекаются.
PENDING и CONFIRMED занимают даты, CANCELED не занимает.

**Зачем блокировка?** Без неё два запроса могли бы одновременно увидеть «свободно»
и оба вставить бронь. С блокировкой второй ждёт завершения первого, затем видит
сохранённую бронь и получает ErrConflict. Это проверено тестом с двумя потоками.

Граница гарантии: бизнес-создание брони должно проходить через BookingService.
Прямой SQL или низкоуровневый bookings.create могут обойти проверку пересечений;
в этой учебной схеме нет PostgreSQL EXCLUDE-ограничения. Для production его можно
добавить отдельной миграцией как дополнительную защиту.

ACID:
A — все операции или ни одной; C — сохранение ограничений;
I — управление взаимодействием параллельных транзакций;
D — подтверждённые изменения сохраняются. Одной транзакции без нужных блокировок
не всегда достаточно для проверки «прочитать свободность, затем вставить».

## Как проверена работа

tests/test_repositories.py содержит 19 интеграционных тестов.
Они обращаются к настоящему PostgreSQL в отдельной БД, а не имитируют ответы.

Проверены: создание/чтение четырёх сущностей; генерация id и времени; отсутствие
записи; дубликаты; пагинация; удаление; SQL-инъекция; UPDATE; FK; CHECK/NULL/UUID;
точность денег; скрытие хеша; COMMIT; ROLLBACK; пересечение; соседние даты;
отмена; два параллельных бронирования; сохранение исходной ошибки; HTTP 200/400/404.

Скрипт verify_lab6.py создаёт новую тестовую БД, применяет миграцию и запускает тесты.
Он дополнительно проверяет, что действительно выполнены все 19 тестов:
«Ran 0 tests, OK» не считается успехом.
После демонстрации удаляется только эта временная БД; основная hotels остаётся.

## Краткие ответы на контрольные вопросы

1. **Что такое Repository?** Отдельный слой работы с хранилищем. SQL сосредоточен
   в одном месте, а HTTP-обработчик занимается запросом и ответом, не таблицами.
2. **Что такое SQL-инъекция и защита?** Ввод пользователя превращается в SQL-команду
   при склейке строк. Параметры передают ввод как данные. Имена таблиц/столбцов и
   направление сортировки выбирают из белого списка.
3. **Зачем доменные ошибки и кто выбирает HTTP-код?** Они избавляют сервис от
   зависимости от драйвера. Репозиторий переводит ошибку базы в доменную;
   HTTP-обработчик переводит доменную в 400/404/409/500.
4. **SQL, Query Builder, ORM?** SQL пишется вручную: полный контроль, больше кода.
   Query Builder собирает SQL из вызовов: удобнее динамические фильтры.
   ORM связывает объекты с таблицами: быстрее CRUD, но запросы и их стоимость
   могут быть неочевидными.
5. **Транзакция, ACID и передача?** Несколько действий как одна операция:
   атомарность, согласованность, изолированность, долговечность.
   В нашем Unit of Work все репозитории используют одно соединение и одну транзакцию.
6. **Зачем уникальный ORDER BY и чем плох OFFSET?** Он задаёт однозначный порядок
   строк, включая одинаковое время создания. Большой OFFSET заставляет базу
   читать и пропускать много строк; keyset-пагинация работает по последнему ключу.
7. **Как интерфейс помогает тестированию?** Сервису передают fake/mock с теми же
   методами, и проверяют бизнес-правила без базы. Интеграционные тесты реального
   репозитория всё равно нужны для проверки SQL и ограничений.
